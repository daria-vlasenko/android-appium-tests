# Android Appium Tests

Автотесты мобильного приложения Android: Appium 2, UiAutomator2, Java 17, JUnit 5, Allure.

Проект — часть портфолио по автоматизации тестирования. Веб-часть: [parabank-ui-tests](https://github.com/daria-vlasenko/parabank-ui-tests), API: [conduit-api-tests](https://github.com/daria-vlasenko/conduit-api-tests).

> **Статус: базовый набор готов.** Покрыты запуск приложения и четыре сценария мобильной специфики: поворот экрана, работа после сворачивания в фон, навигация аппаратной кнопкой, прокрутка списка.

## Объект тестирования

Системное приложение **Настройки Android** (`com.android.settings`).

Выбрано сознательно: приложение есть на любом устройстве и эмуляторе, поэтому тесты воспроизводимы у кого угодно без подготовки APK — и при этом это полноценное приложение с навигацией, длинными списками и вложенными экранами, а не демо-заглушка.

## Покрытие

| Тест | Что проверяет |
|---|---|
| `SmokeTests.appLaunchesAndShowsStartScreen` | приложение запускается, на переднем плане нужный пакет |
| `MobileSpecificTests.survivesScreenRotation` | поворот экрана в альбом и обратно не роняет приложение |
| `MobileSpecificTests.restoresAfterBackground` | приложение восстанавливается после сворачивания в фон |
| `MobileSpecificTests.hardwareBackReturnsToPreviousScreen` | аппаратная «Назад» возвращает на предыдущий экран |
| `MobileSpecificTests.findsElementAfterScrolling` | элемент за пределами экрана находится после прокрутки |

### Почему покрыты именно эти сценарии

Набор собран из того, **чего не существует в вебе**. Проверки, общие для веб и мобильного — заполнение форм, переходы по ссылкам, отображение текста — сознательно не дублируются: они отработаны в веб-проекте.

| Сценарий | Чем специфичен для мобильного |
|---|---|
| Поворот экрана | Android пересоздаёт активность целиком; классическое место потери состояния |
| Сворачивание в фон | система может выгрузить приложение из памяти в любой момент |
| Аппаратная «Назад» | физическая кнопка вне приложения, которой нет в браузере |
| Прокрутка списка | **элемента может не быть в дереве, пока его не проскроллили** — Android переиспользует элементы списка |

Последний пункт — принципиальное отличие от веба. В браузере элемент за пределами экрана всё равно есть в DOM. В Android его физически нет, пока система его не создала, поэтому скролл — не удобство, а единственный способ до него добраться.

## Запуск

Требуется запущенный эмулятор или устройство и поднятый Appium-сервер.

**1. Эмулятор:**

```
emulator -avd <имя>
```

**2. Проверка готовности системы** — обязательный шаг:

```
adb shell getprop sys.boot_completed
```

Должно вернуть `1`. Статус `device` в `adb devices` означает только, что adb достучался до устройства, но **не** что Android закончил загрузку.

**3. Appium-сервер:**

```
appium --address 127.0.0.1
```

**4. Тесты:**

```
mvn clean test
mvn allure:serve
```

Параметры запуска:

```
mvn clean test -Dapp.package=... -Dapp.activity=... -Ddevice.name=... -Dappium.url=...
```

## Принятые решения

**Приложение под тестом вынесено в конфигурацию.** `appPackage` и `appActivity` читаются из параметров запуска. В реальном проекте сюда подставляется APK из артефактов сборки, а не константа в коде.

**Единый подход к конфигурации во всех проектах портфолио.** `MobileConfig` здесь, `Config` в API-проекте и `WebConfig` в веб построены одинаково: параметр запуска, затем переменная окружения, затем значение по умолчанию. Один набор тестов работает на эмуляторе и реальном устройстве, против локального и удалённого сервера — без правок кода.

**Только явные ожидания.** Неявное ожидание (`implicitlyWait`) не используется: при смешивании с явными тайминги складываются непредсказуемо, и тесты начинают мигать.

**Свежая сессия на каждый тест** (`@BeforeEach`, не `@BeforeAll`). Мобильное приложение хранит состояние между экранами — общая сессия делает тесты зависимыми друг от друга.

**Утверждения живут в тестах, а не в Screen Object.** Экран отвечает за то, что на нём есть; тест — за то, каким это должно быть.

**Appium-сервер запускается на `127.0.0.1`.** По умолчанию он слушает на всех интерфейсах и не имеет аутентификации: любой в той же сети получает управление подключёнными устройствами.

**Java 17, не 25.** На Java 25 не стартует агент AspectJ — `Unsupported class file major version 69` — и Allure перестаёт записывать шаги внутри тестов. Версия зафиксирована в конфигурации проекта.

**Названия разделов вынесены в константу.** Тексты в системных Настройках зависят от версии Android и языка системы. Привязка собрана в одном месте, чтобы перенос на другую версию требовал правки одной строки.

## Известные ограничения окружения

**Эмулятор API 36 (Android 16).** Сам эмулятор при запуске предупреждает: `Guest Angle is still unstable for API > 35`. Для стабильных прогонов предпочтительнее обкатанные API 34–35 — иллюстрация к тому, что **самая свежая версия ОС не всегда лучший выбор для автотестов**.

**Снапшоты эмулятора.** Эмулятор сохраняет состояние памяти при закрытии и поднимает его вместо полной загрузки. Повреждённый снапшот даёт систему, которая рапортует о загрузке (`sys.boot_completed=1`), но часть сервисов в ней мертва — Appium падает с `Can't find service: settings`. Лечится холодной загрузкой:

```
emulator -avd <имя> -no-snapshot-load
```

## Структура

```text
src/main/java/com/mobile/
├── config/
│   └── MobileConfig            параметры запуска, адрес сервера, таймауты
└── screens/
    └── SettingsScreen          Screen Object: скролл, навигация, поворот, фон

src/test/java/com/mobile/tests/
├── BaseMobileTest              жизненный цикл драйвера
├── SmokeTests                  запуск приложения
└── MobileSpecificTests         поворот, фон, аппаратная «Назад», прокрутка
```
